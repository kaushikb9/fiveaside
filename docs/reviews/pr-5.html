Restore dedicated unit tests for core/models.py

The domain models lost their behaviors and their test file during an earlier refactor. This PR adds three small, score-derived behaviors back — and the dedicated test module that proves them.

PR #5 · touchline branch: nightshift/item-10 2 files · +98 / −2 additive only

Why this exists

The skeleton (PR #2) had rich models: a Result.winner property derived from scores, Field(ge=0) guarding scores, and Standing.goal_difference — plus a test file for all of it.

When the football-data work (PR #3/#4) reshaped Result into a flat model with a stored winner: str field ("HOME"/"AWAY"/"DRAW"), those behaviors and their test file were dropped. digest.py and football_data.py now depend on that string field, so we can't just revert.

The move: keep the flat shape and the stored winner string exactly as-is. Re-add the lost behaviors as derived properties living alongside the stored field — and restore the dedicated tests, adapted to the flat model.

The flow — what a Result now answers

Two parallel sources of truth, by design. The stored string serves the pipeline; the new properties serve domain logic & tests. They never fight because the properties are computed on read from the scores.

Concepts that may be new

Four ideas do the real work here. None are exotic, but each is a deliberate choice worth seeing clearly.

1 · Validation that lives in the type, not in your code

home_score: int = Field(ge=0) tells pydantic: this field must be ≥ 0. The check runs automatically at construction. There is no if score < 0: raise anywhere — an invalid object simply can't exist. Downstream code never has to defend against a negative score, because one can never be built.

This is the "make illegal states unrepresentable" idea: push the rule to the boundary (object creation) so the rest of the system can assume validity. The test asserts the boundary holds, not the absence of a value:

with pytest.raises(ValidationError):
    _result(-1, 0)

2 · Stored vs. derived — two truths on purpose

winner: str is stored (it comes from the football-data API and the pipeline reads it). winning_team is derived — computed from the scores every time you ask, holding nothing. The PR keeps both rather than picking one.

Why not just compute winner too? Because digest.py and football_data.py already depend on the "HOME"/"AWAY"/"DRAW" string, and the work order forbids touching them. Adding a parallel derived view is the non-breaking way to restore the lost behavior. The trade-off: two representations can drift — but the derived one is always honest about the scores, which is exactly what the domain tests want to check.

3 · Computed properties on a frozen model

The models are frozen=True (immutable — you can't reassign a field after creation). A @property fits this perfectly: it adds behavior without adding mutable state. Calling r.winning_team reads existing fields and returns a value; nothing is cached, nothing is set. Immutability + pure derived reads = no chance of a stale or inconsistent field.

Note the test uses identity, not equality: assert r.winning_team is r.home. Because Team is frozen, the property returns the very same object that was passed in — is is the precise assertion.

4 · A test factory keeps tests about one thing

These frozen models need every field at construction. Rather than repeat ~10 keyword args per test, the file defines small helpers and shared constants:

def _result(home_score, away_score) -> Result:
    return Result(id="1", competition=COMPETITION, kickoff=KICKOFF,
                  home=HOME, away=AWAY,
                  home_score=home_score, away_score=away_score,
                  winner=None, matchday=1, group="Group A")

Now each test varies only the two numbers it cares about — the score behavior is foregrounded, the boilerplate disappears. This mirrors the construction style already used in test_digest.py, so the suite stays consistent.

Decisions & trade-offs

✓ Chosen

  • Keep the flat Result and its stored winner string untouched.
  • Restore behaviors as score-derived properties beside the stored field.
  • Field(ge=0) for score validation — declarative, at the boundary.
  • Core stays pure: only pydantic + stdlib imported.
  • Tests cover exactly the three named behaviors.

⟳ Deferred (on purpose)

  • No reshape back to the old nested fixture= form.
  • No won/draw/lost-vs-played consistency checks.
  • No bounds on points or other fields the roadmap didn't name.
  • No changes to digest.py, football_data.py, render/, or deps.

This is a deliberately thin slice: restore coverage for three behaviors without expanding the models' contract. Anything broader is a separate decision.

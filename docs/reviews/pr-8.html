Football client handles null/TBD team names

One unresolved knockout fixture used to blank out the entire live football section. Now those fixtures show up labeled TBD — everything else keeps flowing.

PR #8 branch: nightshift/item-14 3 files · +57 −3 parsing only — no model / renderer changes

The problem in one picture

During the live World Cup, terrace digest suddenly showed no football at all. The cause was a single field. football-data.org returns "name": null for a team that hasn't been decided yet (e.g. "winner of Round of 16, match 49"). That one null detonated the whole parse.

API payload — 20 matches, 19 fine, 1 with name:null
│ loop over matches in _parse_matches
_team({"name": null}) → Team(name=None) → pydantic ValidationError (name is typed str)
│ ValidationError is a ValueError
fetch_matches's except (KeyError, TypeError, ValueError) swallows it
↓
SourceResult(ok=False, fixtures=[], results=[])  all 20 dropped

The exception handler is broad on purpose — it protects the digest from a malformed payload. The bug is that a normal knockout value looked like a malformed payload. So the safety net suppressed good data.

The flow after the fix

The fix lives entirely in the source adapter. Two small guards stop the exception from ever firing, so the broad handler never trips on this case.

guard 1 · null name
_team coerces a missing / null / blank name to "TBD". code stays whatever tla gives (may be None).
guard 2 · null object
_parse_matches uses match.get("homeTeam") or {} so even a wholly-null team object becomes an empty dict before it reaches _team.
API payload — 20 matches incl. TBD knockout
↓
every team resolves to a valid Team — name="TBD" when unknown
↓
SourceResult(ok=True, fixtures=[20], results=[2])  nothing dropped

The actual change

# src/terrace/sources/football_data.py
+_TBD_NAME = "TBD"

 def _team(payload: dict[str, Any]) -> Team:
-    return Team(name=payload.get("name", ""), code=payload.get("tla"))
+    name = payload.get("name") or ""
+    return Team(name=name.strip() or _TBD_NAME, code=payload.get("tla"))

     for match in payload.get("matches", []):
         ...
-        home = _team(match.get("homeTeam", {}))
-        away = _team(match.get("awayTeam", {}))
+        home = _team(match.get("homeTeam") or {})
+        away = _team(match.get("awayTeam") or {})

Why payload.get("name") or "" instead of .get("name", "")? Because the key exists — its value is JSON null. A default only kicks in when the key is absent. or "" handles the present-but-null case, then .strip() or _TBD_NAME also catches whitespace-only names. Same trick with or {}: the key is present with value null, so the default {} never fired.

Concepts that may be new

1 · A validation error is a ValueError

The Team model declares name: str. Passing None raises a pydantic ValidationError — which subclasses Python's built-in ValueError. That inheritance is the whole bug: fetch_matches wraps parsing in except (KeyError, TypeError, ValueError) to survive junk payloads, and a ValidationError slips right into that net. So a perfectly normal knockout value was treated like corrupt data. Worth internalizing: broad except ValueError blocks will also catch your model-validation failures.

2 · Normalize at the boundary, not in the model

The tempting fix is to loosen the model: name: str | None. This PR deliberately doesn't. The repo's convention (AGENTS.md) is that I/O quirks live in sources/ — the adapter that touches the outside world — while core/models.py stays a clean, strict contract. The "outside is messy, inside is clean" boundary means every other part of the app can trust that Team.name is always a real string. The mess is absorbed in exactly one place.

3 · frozen=True models

Team is declared class Team(BaseModel, frozen=True) — immutable and hashable once built. That's why coercion happens before construction (in _team), not by mutating the object after. You can't reach in and patch name later; you decide the value at the moment of creation. Immutable value objects like this are safe to share, compare, and cache without worrying about something changing them underneath you.

4 · Label, don't skip — graceful degradation

Two ways to survive a TBD team: drop the match, or keep it with a placeholder. The PR keeps it. A knockout bracket where the fixtures vanish until teams are decided is worse than one that says "TBD vs Brazil, July 5." The existing renderer just prints Team.name, so "TBD" displays for free — no renderer change needed. Degrade the data quality, preserve the user's view.

5 · The regression test guards the failure mode, not just the feature

The important assertion isn't "TBD shows up" — it's that one bad match doesn't silently delete the good ones:

# the real symptom that was reported
assert len(result.fixtures) == len(payload["matches"])  # nothing dropped
assert len(result.results) == 2                          # resolved games intact
assert mex_can.home_score == 2                           # a real result still parses

It also pins the labeling contract: home.name == "TBD" and home.code is None for the unresolved side. A test that only checked the happy path would pass even if the suppression bug came back.

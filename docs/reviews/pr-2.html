01The flow

One public entry point: FootballDataClient.fetch_matches("WC"). It does a single HTTP GET, then folds the response into normalized models. Everything funnels into one return type — SourceResult — whether the call succeeds or fails.

Key shape: one API call returns both scheduled and finished matches in the same matches array — so a single fetch yields fixtures and results. Every match becomes a Fixture; the finished-with-a-score subset is also promoted to a Result.

03Concepts that may be new

1 · Protocol typing — a duck-typed interface

MatchSource isn't a base class anyone inherits. It's a typing.Protocol: a declaration that says “anything with a method fetch_matches(competition) -> SourceResult counts as a source.”

@runtime_checkable
class MatchSource(Protocol):
    def fetch_matches(self, competition: str) -> SourceResult: ...

FootballDataClient never says class …(MatchSource) — it just happens to match the shape, so it qualifies (structural typing). The test src: MatchSource = client type-checks, and @runtime_checkable lets isinstance(client, MatchSource) pass at runtime too.

Why here: the next source (a different API, a fake for tests) only has to match the shape — no shared base class, no import coupling. The seam is the method signature, nothing more.

2 · Graceful degradation via a result object

Instead of letting an HTTP error bubble up as an exception, the client always returns a SourceResult. Failure is data, not a crash.

try:
    response = self._client.get(url)
    response.raise_for_status()        # 4xx/5xx → raises
    payload = response.json()          # bad body → raises
except httpx.HTTPError as exc:    # network, timeout, 429, 500…
    return SourceResult(ok=False, fixtures=[], results=[], error=str(exc))
except ValueError as exc:       # JSON decode
    return SourceResult(ok=False, …, error=f"invalid JSON: {exc}")

Three failure classes are caught — transport errors, bad status codes, and unparseable bodies (plus a third try/except around parsing for unexpected payload shapes).

Why here: a daily digest must still render if one source is down. Callers branch on result.ok — a boolean — instead of wrapping every call in their own try/except. The error contract lives in one place.

3 · Dependency injection of the HTTP client

The constructor accepts an optional client: httpx.Client. In production it's None, so the class builds its own (with auth header + timeout). In tests, a pre-wired client is injected.

self._client = client or httpx.Client(
    headers={"X-Auth-Token": self.token} if self.token else {},
    timeout=timeout,
)

That one seam is what makes the whole test suite network-free — httpx.MockTransport(handler) intercepts every request and returns whatever response the test wants:

# the test fakes the API in ~3 lines
transport = httpx.MockTransport(handler)   # handler(request) -> Response
FootballDataClient(token="dummy", client=httpx.Client(transport=transport))

Why here: fast, deterministic, offline tests that still exercise the real request-building and response-parsing code paths — not a mock of the client itself.

4 · Frozen pydantic models as the normalized vocabulary

SourceResult, Fixture, Result are all BaseModel, frozen=True — validated on construction and immutable after. The client's job is translation: messy external JSON → this fixed internal vocabulary.

football-data says "TIMED"; the domain only knows MatchStatus.SCHEDULED. A small map does the normalizing so the rest of the app never sees vendor strings:

SCHEDULED / TIMED → SCHEDULED IN_PLAY / PAUSED → LIVE FINISHED → FINISHED

Why here: immutability means a Result can't be mutated downstream, and the status map means the World-Cup-specific source stays the only place that knows football-data's vocabulary. core/ stays pure.

5 · Fixture-based (“recorded response”) tests

wc_matches.json is a real, hand-trimmed v4 payload checked into the repo. Tests load it and assert against known values — e.g. match 1001 is Mexico 2–1 Canada, winner HOME; match 1003 is group "Group A", status SCHEDULED.

The same fixture is mutated in-memory to cover edge cases without new files — e.g. appending a FINISHED match with a null score to prove it becomes a Fixture but not a Result, or del payload["competition"] to test the fallback to the passed competition code.

Why here: the trimmed JSON documents exactly what shape the parser expects; if football-data changes its schema, these tests are the canary.

04Decisions & trade-offs

Chosen

  • One endpoint (/matches) yields fixtures + results together.
  • Fetch the whole competition list; filter nowhere.
  • Default competition="WC" as a method arg — client stays competition-agnostic.
  • Token falls back to FOOTBALL_DATA_TOKEN env var.
  • httpx only — pre-approved, no new deps beyond it.

Deferred (next slices)

  • Standings / group-table parsing (Night-2 roadmap).
  • Pagination, date-range filtering.
  • Rate-limit / retry handling (note: 429 just degrades for now).
  • Caching, async.

Thin-slice discipline: core/, render/, web/ and the docs are untouched — no user-visible command changed.

05How to see it work

# install deps (httpx + pydantic now locked)
uv sync

# run the suite — fully offline, 11 tests
uv run pytest tests/test_football_data.py -v

# lint clean
uv run ruff check .

No API token needed to run the tests — MockTransport stands in for the network. To hit the live API, set FOOTBALL_DATA_TOKEN and call FootballDataClient().fetch_matches("WC") from a REPL.

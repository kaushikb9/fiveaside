NewsSource interface + RSS fetch (parsing only)

Add a clean, testable seam for pulling football headlines from RSS feeds into pure domain objects — no digest wiring yet. This slice is all plumbing and parsing.

+ NewsItem model + NewsSource protocol + RSSNewsClient stdlib XML, no new deps 19 tests

The flow

A caller asks the client for news. The client hits each configured feed, hands the raw bytes to a pure parser, and collects NewsItems into one NewsResult. Failures are absorbed at the edges so one bad feed (or one bad item) never blanks the rest.

callerholds an RSSNewsClient, calls .fetch_news()
↓
RSSNewsClient.fetch_news() loops over feeds = [(label, url), …]  ·  GET each via injected httpx.Client
↓   response.content (bytes) per feed
_parse_rss(content, label)  pure function ElementTree → iterate every <item> independently → build valid NewsItems
↓   list[NewsItem]
NewsResult accumulate items across feeds, decide ok / error

The decision at the end is the interesting part — it encodes graceful degradation:

no feeds configured ok=True   items=[]   — trivially fine
some feeds fail ok=True   items = whatever succeeded   — partial data still ships
all feeds fail ok=False   items=[]   error = "label: reason; …"

Same shape as the existing SourceResult for match data — callers already know how to read an ok flag and ignore the rest on failure.

Concepts that may be new

These are the ideas worth slowing down on — each is a deliberate design choice, not incidental.

1 · Protocol typing (structural “interfaces” in Python)

Python has no interface keyword. A typing.Protocol fills that gap: it defines a shape — “anything with a fetch_news() -> NewsResult method” — without requiring classes to inherit from it.

@runtime_checkable
class NewsSource(Protocol):
    def fetch_news(self) -> NewsResult: ...

RSSNewsClient never says class RSSNewsClient(NewsSource). It simply has the right method, so isinstance(client, NewsSource) is True (that’s what @runtime_checkable enables, and a test asserts it).

Why here: the digest layer (a later slice) can depend on the NewsSource shape, and a real RSS client, a cache, or a fake test double can all satisfy it independently. Loose coupling without an inheritance tree.

2 · Dependency injection of the HTTP client

The constructor takes an optional client: httpx.Client. In production it’s None, so the class builds its own. In tests, the suite passes a client wired to httpx.MockTransport that returns the fixture bytes — no socket ever opens.

def __init__(self, feeds=None, *, client=None, timeout=10.0):
    self.feeds = feeds if feeds is not None else list(_DEFAULT_FEEDS)
    self._client = client or httpx.Client(timeout=timeout)

Why here: the network is the one thing you can’t test reliably. Injecting the client makes every behavior — happy path, HTTP 500, malformed XML — a deterministic unit test. This mirrors how FootballDataClient is already tested in the repo.

3 · Frozen pydantic models

NewsItem and NewsResult are declared frozen=True — immutable after construction. Pydantic still validates types on the way in (a title must be str; published is datetime | None).

class NewsItem(BaseModel, frozen=True):
    title: str
    link: str
    source: str            # human label, e.g. "BBC Sport"
    published: datetime | None = None
    summary: str | None = None

Why here: a parsed headline is a value, not a record you mutate. Freezing makes items safe to pass around and cache, and keeps the core layer disciplined (pydantic + stdlib only — no I/O leaks into the domain).

4 · Per-record tolerance vs. all-or-nothing parsing

This is the heart of the PR. A naive parser wraps the whole feed in one try/except — so a single malformed <item> nukes every headline. Instead the parser loops item by item and skips only the bad ones.

for item_el in root.iter("item"):
    try:
        title = (title_el.text or "").strip() if title_el is not None else ""
        link  = ...
        if not title or not link:
            continue                 # skip, don't crash
        published = None
        try:
            published = parsedate_to_datetime(pub_date_el.text.strip())
        except Exception:
            published = None        # bad date -> keep item, drop the date
        items.append(NewsItem(...))
    except Exception:
        continue                     # one bad item never suppresses the rest

The fixture proves both branches: item #3 has no <title> (skipped → 5 items become 4), and item #4 has pubDate = "NOT A DATE AT ALL" (kept, with published=None).

Why here: RSS in the wild is messy. Codifies a hard-won team lesson — broad try/except at the wrong granularity silently blanks whole sections. The fix is to fail at the smallest unit, the individual record.

5 · Standard-library XML — deliberately no feedparser

Parsing uses xml.etree.ElementTree and dates use email.utils.parsedate_to_datetime (RSS pubDate is RFC-822, the same format email headers use). Both ship with Python.

Why here: the work order explicitly bans new dependencies. The convenient choice (feedparser) buys little for a trimmed feed and adds supply-chain + maintenance weight. Hand-rolling ~40 lines against stdlib keeps pyproject.toml untouched.

Decisions & trade-offs

Chosen: two failure boundaries. A pure _parse_rss() with no I/O, and a thin fetch_news() that owns networking and the ok/error decision. Pure logic is trivially testable; impure edges stay small.
Chosen: the list[(label, url)] shape supports many feeds today, but only one BBC fixture is shipped. The multi-feed accumulation and partial-failure logic are already written and tested via in-test feeds — the interface won’t churn when a second feed lands.
Deferred (on purpose): digest wiring, attaching headlines to sections, relevance scoring, dedup, and any second live feed. This slice changes no user-visible output — it only adds a seam. Keeping it single-surface is itself a lesson applied (fat multi-file items blow the budget).
Trade-off: a bare except Exception guards both the per-item loop and the per-feed loop. Broad, but intentional and tightly scoped — the goal is resilience, and each guard wraps exactly one record/feed so nothing wider is swallowed.

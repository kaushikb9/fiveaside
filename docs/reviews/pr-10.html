PR #10 · touchline · nightshift/item-19

Attach top-3 relevant headlines to each digest section

Each section of the daily digest now carries the three football headlines most about the teams playing in it — so "what's being written about" sits right next to the results and fixtures, without leaving the digest.

Thin slice. Touches only the core selection logic, the Markdown renderer, and the CLI wiring. Deferred on purpose: web/HTML rendering of headlines, per-match-card headlines, any new model, and any change to the news sources. The NewsItem / NewsSource interface is consumed as-is.

1The flow

Two independent inputs — match data and news — converge in the pure core, where headlines are scored against the teams in each section. The render and CLI layers stay thin.

Note the split: today_headlines is computed from today's fixture teams; yesterday_headlines from yesterday's result teams. Match-of-the-day reuses today_headlines — there's deliberately no third list.

3Concepts that may be new

A scored, deterministic ranking (not just a filter)

The heart of the change is one pure function. Relevance is just a count: how many distinct section-team names appear (case-insensitive substring) in a headline's title. Summary is ignored on purpose — to keep results predictable.

for idx, item in enumerate(news):
    title_lower = item.title.lower()
    score = sum(1 for t in team_set if t in title_lower)
    if score >= 1:
        scored.append((score, item, idx))

The interesting part is the total ordering. Ties are broken so the output is stable run-to-run — essential for snapshot tests and a calm reader experience:

sort key = (-score, -published.timestamp(), idx)
            #  most teams  → newest first   → original order

Why right here: a transparent integer score beats an opaque "ML relevance" black box for a digest. It's testable, explainable, and fast — and idx as the final tiebreaker guarantees there's never an ambiguous result.

Sentinels for "missing" sort values

published is datetime | None. You can't compare None against a timestamp, so undated items are pushed to the end with float("inf") — and the .timestamp() call is wrapped so an odd date can't crash selection.

if item.published is None:
    pub_sort = float("inf")   # undated → sorts last
else:
    pub_sort = -item.published.timestamp()  # newest → smallest → first

Why right here: negating the timestamp turns "newest first" into a plain ascending sort, so the whole key is a single tuple — no custom comparator, no reverse flags.

Dedupe-after-sort, keyed by link

The same story can appear in multiple feeds. Deduping happens after sorting and keeps the first (highest-ranked) occurrence — so you never drop the better-placed copy.

seen_links = set()
for _score, item, _idx in scored:
    if item.link not in seen_links:
        seen_links.add(item.link)
        result.append(item)
        if len(result) == limit: break

Order matters: dedupe-then-sort could keep a worse-ranked duplicate. Sort-then-dedupe is the correct sequence.

Additive, defaulted change — nothing existing breaks

Two new fields default to []; the new news argument is keyword-only and defaults to None. Every prior caller and snapshot test stays green untouched.

class DailyDigest(BaseModel, frozen=True):
    ...
    yesterday_headlines: list[NewsItem] = []
    today_headlines: list[NewsItem] = []

def build_digest(fixtures, results, *, now, news: list[NewsItem] | None = None): ...

The renderer mirrors this: it emits the **In the news** header only when the list is non-empty, so an empty section renders byte-identically to before.

Why right here: a frozen pydantic model with defaulted fields lets you grow the data shape without a migration or a breaking signature. The empty-list default is the graceful path.

Dependency injection + graceful degradation in the CLI

The news source is passed in (injected), not constructed inside the logic — so tests feed a fake source and a fixed clock. And a news failure never sinks the digest: it still renders, with a warning appended.

news_items = None
if news_source is not None:
    news_res = news_source.fetch_news()
    news_items = news_res.items
    if not news_res.ok:
        news_error = news_res.error
...
if news_error is not None:
    output += "\n> ⚠️ Some news was unavailable: ..."

Why right here: news is a nice-to-have layered onto must-have match data. Mirroring the existing match-source warning keeps the failure UX consistent, and the NewsSource Protocol means the CLI depends on a shape, not a concrete class.

Purity guard: the core stays import-clean

digest.py imports only stdlib + terrace.core.models. The selection logic needed NewsItem — already in core.models — so no forbidden sources import sneaks in. An existing test (test_digest_module_has_no_forbidden_imports) enforces this.

Why it matters: keeping the core free of I/O and adapter imports is what makes relevant_headlines trivially unit-testable with plain lists.

4Decisions & trade-offs

Chosen

  • Title-only matching — predictable, no summary noise.
  • Substring, case-insensitive — simple; "Spain" matches "Spain's…".
  • Cap at 3, deduped by link.
  • Reuse today_headlines for match-of-the-day.
  • Injected source + defaulted args throughout.

Deferred

  • Web/HTML rendering of headlines (web/app.py + template).
  • Per-match-card headlines (sections only for now).
  • No new model; NewsItem reused as-is.
  • No changes to sources/ (rss, base, football_data).
  • No README / CLI-flag changes — behavior is automatic.

Trade-off worth naming: substring matching can over- or under-match (a short team name buried in another word, or an official name that differs from the headline's wording). Acceptable for a digest, and easy to tighten later since it's one isolated, tested function.

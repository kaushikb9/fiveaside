FastAPI web surface: the daily digest as an installable PWA

A new terrace.web package wraps the existing digest pipeline in a FastAPI app so a phone or Mac can open / and see today's football as a clean, mobile-first page that Safari/Chrome offer to "install" like a native app — no new business logic, no App Store.

+652 lines   11 files · all additive. The core/, sources/, render/, and cli.py were deliberately left untouched — this PR only adds a new surface on top.

The flow — one request, end to end

When a browser hits GET /, the handler reuses the exact same two-step pipeline the CLI already uses (fetch → build), then hands the result to a Jinja template instead of printing markdown.

BrowserGET /
→
index()web/app.py
↳
source.fetch_matches("WC")returns SourceResult(ok, fixtures, results, error)
↳
build_digest(fixtures, results, now=now_fn())pure core → DailyDigest (frozen)
↳
TemplateResponse("digest.html", …)passes digest + degraded flag + error
digest.html (Jinja2)mobile-first HTML + inline CSS
→
Browser renders+ registers /sw.js

Three other routes make it a Progressive Web App rather than just a page:

GET /manifest.webmanifestapp identity & icons → "Add to Home Screen"
GET /sw.jsservice worker, served at root scope so it can control /
GET /static/…StaticFiles mount → icons, etc.
The key design move: the route handler is a thin adapter. It does no football logic of its own — it borrows fetch_matches + build_digest (the same pair cli.run_digest calls) and only translates the result into HTML. That's why the diff touches no existing modules.

Concepts that may be new

1 · The app factory + dependency injection

Instead of building one global app with a hard-wired data source, the code exposes a function that builds the app and lets the caller pass in its dependencies:

def create_app(
    source: MatchSource | None = None,
    *,
    now_fn: Callable[[], datetime] | None = None,
) -> FastAPI:
    if source is None:
        source = FootballDataClient()        # real default
    if now_fn is None:
        def now_fn(): return datetime.now(UTC)
    ...
    return app

app = create_app()   # production instance, used by uvicorn

The two injected things are exactly the two sources of nondeterminism: the network (source) and the clock (now_fn). Tests pass a _FakeSource and a fixed NOW, so a test can assert "this exact fixture renders with this exact kickoff label" with zero flakiness and zero network.

Why it's the right call here: it keeps the app global that uvicorn needs (terrace.web.app:app) and makes every behaviour testable, without mocking or monkeypatching. One small seam buys full control.

2 · Lazy network — nothing touches the wire at import

The default FootballDataClient() is constructed when the app is built but doesn't call the API until fetch_matches runs inside a request. So importing terrace.web.app (which uvicorn and pytest both do) is free and offline. There's even a test guarding this:

def test_create_app_default_does_not_touch_network_at_construction():
    app = create_app()      # no .get("/") → no fetch → no network
    assert app is not None

Why it matters: import-time side effects are a classic source of slow, brittle test suites and surprise outbound calls. Keeping construction pure is a discipline worth recognising.

3 · Graceful degradation, mirrored from the CLI

A data source can fail. The SourceResult carries an ok flag and an error string rather than throwing. The handler never branches on success — it always builds a digest from whatever came back, and passes the failure state into the template as a flag:

app.py 
res = source.fetch_matches("WC")
digest = build_digest(res.fixtures,
                      res.results,
                      now=now_fn())
return templates.TemplateResponse(
  request, "digest.html", {
    "digest": digest,
    "degraded": not res.ok,
    "error": res.error,
})
digest.html 
{% if degraded %}
<div class="banner">
  ⚠️ Some data was
  unavailable: {{ error }}
</div>
{% endif %}

A failed fetch still returns 200 with an empty-but-valid digest and a visible amber banner — never a 500, never a blank page. The failure-mode test asserts the body contains both the banner text and the raw error boom.

Why it's the right call: a daily-glance app should always show something. Degrading to "here's the page, plus a note that data was thin" is far better UX than an error screen — and it reuses the exact error-handling shape the CLI already established.

4 · What makes it a PWA (and the service-worker scope trick)

Three browser-platform pieces turn an ordinary page into an installable app:

  • Manifest — JSON describing the app's name, colors, start_url:"/", display:"standalone", and icons. This is what makes Safari/Chrome offer "Add to Home Screen."
  • Service worker (sw.js) — a script the browser runs in the background. On install it caches the "app shell" (/, manifest, icons); on fetch it serves cache-first, falling back to network. That's what lets the installed app open instantly / offline.
  • Icons + <head> meta — apple-touch-icon, theme-color, viewport, and an inline script that registers the worker.

The subtle bit is why /sw.js gets its own route instead of being served from /static/sw.js:

@app.get("/sw.js")
def service_worker():
    return FileResponse(STATIC_DIR / "sw.js", media_type="text/javascript")

A service worker can only control pages at or below its own URL path ("scope"). Served from /static/sw.js its scope would be /static/ — useless, since the page lives at /. Serving it from the root path gives it root scope, so it can control /. Same reasoning gives the manifest its own route with the precise application/manifest+json media type.

Why it's the right call: these are platform contracts, not preferences. Getting scope and media types exactly right is the difference between "installable" and "browser silently ignores it."

5 · The template is the renderer (for now)

There's no render/html.py module. The Jinja2 template does the rendering directly — looping digest.today into match cards, printing card.kickoff_label, and reusing the same empty-state copy as the markdown renderer (Nothing finished yesterday. / No matches today.). The CSS is inlined in a single <style> block: system font stack, single column, no CDN, no framework.

Why deferred-but-fine: a second renderer module would be premature abstraction for one template. If a third surface needs shared HTML logic later, that's when you extract it.

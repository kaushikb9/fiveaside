01 The flow — where this sits

terrace is built as a pure core surrounded by adapters. This PR lays down the four rooms and furnishes the first one (the data models). Nothing here touches the network or the disk — that comes in later PRs, on the edges.

the world ──▶ sources/ ──▶ core/ ──▶ render/ ──▶ you (football API, (the models in (markdown, RSS — PR #2+) THIS PR; digest web — later) logic later) │ │ fetches raw pure data + rules, data, maps it no I/O, fully testable into core types ▲ │ web/ (FastAPI surface, later) THIS PR ships: the four empty rooms + core/models.py (the vocabulary)

Why this matters: every later PR plugs into one room without disturbing the others. A football-API change touches only sources/; a new screen touches only render/ or web/. The core never has to know.

03 Concepts worth pausing on

Frozen models (immutability)

Every model sets model_config = ConfigDict(frozen=True). Once you build a Fixture, you can't mutate it — assignment raises.
Why it's right here: these objects represent facts (a match, a result). Facts shouldn't be quietly edited after creation; if something changes, you make a new one. Frozen data is also safe to pass around, cache, and compare without worrying that some far-off function mutated it behind your back. It's the data-modelling equivalent of "no surprises."

Competition-agnostic by composition

The World Cup is nowhere hardcoded in the models. Instead, Fixture has a Competition field. The same types model a Chelsea league game or a World Cup final. 
class Fixture(BaseModel):
    competition: Competition   # ← the comp is data, not a hardcoded assumption
    home: Team
    away: Team
    kickoff: datetime
    group: str | None = None   # optional: WC has groups, leagues don't
Why it's right here: the roadmap's "later" section turns terrace into a club companion. Because the comp is just a field, that future is a config change, not a rewrite. This is "composition over hardcoding" — model the variable thing as data.

Computed properties (derive, don't store)

Result.winner and Standing.goal_difference aren't stored fields — they're computed from the data on access. 
    @property
    def winner(self) -> Team | None:
        if self.home_score > self.away_score: return self.fixture.home
        if self.away_score > self.home_score: return self.fixture.away
        return None   # a draw — note it can't lie about the score
Why it's right here: a stored winner could drift out of sync with the score. A derived one is always correct by construction, and the draw case (None) is handled honestly instead of being a special string.

Validation at the boundary (Field(ge=0))

Scores and match counts declare Field(ge=0) — pydantic rejects a negative at construction time with a ValidationError. The test deliberately proves it: Result(home_score=-1, ...) raises.
Why it's right here: a negative score is nonsense; catching it the instant bad data tries to become a model means the rest of the code never has to defend against it. Validate once, at the edge, then trust the type everywhere inside.

Testing the failure, not just the happy path

The rubric the grader enforces requires at least one failure-mode test. Here it's the negative-score rejection — a test that asserts the code says no correctly.
Why it's right here: happy-path tests tell you the code works when everything's fine; failure tests tell you it fails safely when it isn't. The second kind is where real bugs hide. Good habit to expect in every PR.

04 Decisions & trade-offs

  • pydantic over plain dataclasses — chosen for free validation and clean JSON parsing later (the football API returns JSON; pydantic maps it in PR #2 with no hand-written parsing).
  • Models only, no logic — the lead deliberately kept this slice to the vocabulary. Digest rules and data-fetching are separate PRs. Thin slices stay reviewable and keep the repo green.
  • Deferred: any I/O, the digest, the web surface — all later roadmap items that build on these types.

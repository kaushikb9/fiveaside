Group standings on the web app

A new /standings page renders the World Cup group tables — one table per group, in finishing order — fed by the same football-data.org client, with a link from the digest home page.

The flow

A browser hits /standings. The route asks the source for the table, reshapes a flat list into per-group buckets, and hands it to a template. Nothing in the app computes positions — it trusts the API's ordering and just displays it.

→
source.fetch_standings("WC")FootballDataClient → HTTP GET
→
_parse_standingsJSON → list[Standing], per-row
StandingsResultok · standings · error
→

The endpoint called is {base_url}/competitions/WC/standings. The API returns several "views" of each group (HOME / AWAY / TOTAL); the parser keeps only type == "TOTAL".

Key idea: the page is a read-only projection. No tie-break rules, no recomputation of points — the API already ordered the rows, and this PR deliberately trusts that order (a "thin slice").

Concepts that may be new

1 · Protocol typing — a contract without inheritance

Instead of a base class the client must subclass, StandingsSource is a typing.Protocol. Any object with a method of the right shape structurally satisfies it — no class FootballDataClient(StandingsSource) needed.

@runtime_checkable
class StandingsSource(Protocol):
    def fetch_standings(self, competition: str) -> StandingsResult: ...

Because it's @runtime_checkable, the test can literally assert isinstance(client, StandingsSource). This is "duck typing with a type checker watching" — the web app depends on the shape, so the test _FakeSource slots in with zero ceremony. That's how the route tests run with no network.

2 · Graceful degradation as a return value, not an exception

A flaky upstream should never 500 the page. So fetch_standings never lets a network/JSON error escape — it catches and returns a result object that says "not ok, here's why."

try:
    response = self._client.get(f"{self.base_url}/competitions/{competition}/standings")
    response.raise_for_status()
    payload = response.json()
except httpx.HTTPError as exc:
    return StandingsResult(ok=False, standings=[], error=str(exc))
except ValueError as exc:                       # bad JSON
    return StandingsResult(ok=False, standings=[], error=f"invalid JSON: {exc}")

The route reads res.ok and passes degraded=not res.ok to the template, which shows the amber banner "⚠️ Some data was unavailable". Same contract the home page already uses — consistency for free. The failure-mode test confirms /standings still returns 200 with the error text instead of crashing.

3 · Per-row tolerance — one bad row can't blank the table

This is the sharpest lesson baked in. The try/except is inside the row loop, not around the whole parse. A single malformed record is skipped; the rest of the table survives.

for row in group_entry.get("table", []):
    try:
        standings.append(Standing(
            position=row["position"], team=_team(row.get("team") or {}),
            played=row["playedGames"], ... ))
    except (KeyError, TypeError, ValueError, ValidationError):
        continue   # skip this row, keep the others

The fixture proves it: Group A's table has 5 rows, but one (BAD_ROW_NO_POSITION) is missing its position key. The test asserts 8 standings parse (4 + 4), not 9, and that the bad team never appears. Had the try wrapped the whole loop, that one row would have wiped the entire group.

Note the reused _team() helper: a missing/blank name coerces to "TBD" rather than failing — same coercion used for match teams.

4 · Frozen models & the "view filter"

Standing (and StandingsResult) are BaseModel, frozen=True — immutable once built, so a result can't be mutated downstream and goal_difference is a computed property, never a stored field that could drift. Also note the API returns multiple perspectives of each group; the parser keeps only the cumulative one:

if group_entry.get("type") != "TOTAL":
    continue   # skip HOME / AWAY split tables

5 · Shaping data in the route, not the core

The source returns a flat list[Standing]. The page wants buckets per group, each sorted. That reshaping lives in the route — a few lines, no new core module:

groups: dict[str, list[Standing]] = {}
for s in res.standings:
    groups.setdefault(s.group or "Unknown", []).append(s)
groups = {k: sorted(v, key=lambda x: x.position)
          for k, v in sorted(groups.items())}

Why here and not in core? Grouping is a presentation concern for this one page. Keeping it in the route preserves the rule that the core stays pure and display-agnostic.

Decisions & trade-offs

Chosen

  • Trust the API's row order — render as given.
  • Reuse the existing Standing model unchanged.
  • Group/sort in the route; template just iterates.
  • Reuse digest's PWA head + styles for visual consistency.
  • Errors surface as data (ok=False + banner), never exceptions.

Deferred (out of scope)

  • No CLI standings command.
  • No markdown / digest-core changes.
  • No client-side recompute or tie-break logic.
  • No knockout / bracket stages.
  • No new dependencies; pyproject.toml untouched.
